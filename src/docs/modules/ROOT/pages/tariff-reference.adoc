= Tariff reference
:description: Every charge type a plan file can contain, and the fields each takes.

A plan file has identity fields and a list of `charges`. This page documents both.

== Plan fields

[cols="1,1,3"]
|===
| Field | Required | Meaning

| `id` | yes | Unique identifier. Keep it stable; it is how the plan is referred to.
| `name` | yes | Display name, shown in the comparison.
| `retailer` | yes | Who sells it. Use `Unknown` if you are still finding out.
| `zone` | yes | Distribution zone. See <<zones>>.
| `gstInclusive` | yes | Whether the rates below include GST. No default — see
xref:defining-a-plan.adoc#gst[GST].
| `validFrom` | no | ISO date. Omit for unbounded.
| `validTo` | no | ISO date. Omit for unbounded.
| `charges` | yes | At least one. See <<charges>>.
|===

A plan must have exactly one *usage* charge — one of `flatRate`, `timeOfUse` or `tiered` — and at
most one `dailySupply`.

[#zones]
== Distribution zones

`AUSNET`, `CITIPOWER`, `POWERCOR`, `UNITED_ENERGY`, `JEMENA`, `OTHER`.

Your zone is determined by where you live, not who you buy from. The first four digits of your NMI
identify it: `6305` is AusNet.

[#charges]
== Charge types

=== dailySupply

A fixed charge per day of supply, regardless of consumption. Counted from the distinct calendar
dates present in your data, so a daylight-saving day still bills as one day.

[source,yaml]
----
- type: dailySupply
  cents: 123.20
----

=== flatRate

One rate for all consumption.

[source,yaml]
----
- type: flatRate
  cents: 31.98
----

=== timeOfUse

Usage priced by when it was consumed. Takes a list of `bands`, each with `from`, `to`, optional
`days` (default `ALL`) and `cents`. Bands must cover the whole day exactly once — see
xref:defining-a-plan.adoc#tiling[Bands must tile the day].

[source,yaml]
----
- type: timeOfUse
  bands:
    - { from: "16:00", to: "21:00", days: ALL, cents: 47.64 }
    - { from: "11:00", to: "16:00", days: ALL, cents: 17.59 }
    - { from: "21:00", to: "11:00", days: ALL, cents: 22.60 }
----

`days` accepts `ALL`, `WEEKDAYS`, `WEEKENDS`, `BUSINESS_DAYS`. `BUSINESS_DAYS` excludes public
holidays; `WEEKDAYS` does not.

Real Victorian plans often cap their cheap windows rather than pricing them flat. A plan might
price the first 50 kWh of each day's 11:00-15:00 consumption at nothing and the rest of that
window at a small rate, while its peak window carries its own independent daily kWh block. A band
supports this by declaring `tiers` and `reset` instead of `cents`: a band must declare exactly one
of `cents` or `tiers`, and declaring both is rejected. `reset` is required when `tiers` is used,
and rejected alongside `cents`; it accepts the same values as the `tiered` charge type described
below on this page — `DAILY`, `MONTHLY`, `QUARTERLY`, `ANNUAL`. The tier rules are shared too: the
last tier must have no `upToKWh` — it is the unbounded balance — and thresholds must ascend.

[source,yaml]
----
- type: timeOfUse
  bands:
    - from: "11:00"
      to: "15:00"
      days: ALL
      reset: DAILY
      tiers:
        - { upToKWh: 50, cents: 0.0 }
        - { cents: 9.405 }
    - from: "15:00"
      to: "11:00"
      days: ALL
      reset: DAILY
      tiers:
        - { upToKWh: 15, cents: 31.559 }
        - { cents: 33.963 }
----

Each band accumulates its own allowance separately — two capped bands on the same plan never
spend each other's kWh. This carries through to the bill breakdown, which must reconcile line by
line against a retailer's: a capped band produces one line per block, labelled
`Usage 11:00-15:00 to 50 kWh` and `Usage 11:00-15:00 balance`. A band priced with plain `cents`
keeps the single, unsuffixed line it has always had — `Usage 16:00-21:00`, say. Tiling is
unaffected either way: capped or not, bands must still cover the whole day exactly once.

=== tiered

Block rates that reset periodically. The last tier must have no `upToKWh` — it is the unbounded
balance. Thresholds must ascend.

[source,yaml]
----
- type: tiered
  reset: QUARTERLY          # DAILY | MONTHLY | QUARTERLY | ANNUAL
  tiers:
    - { upToKWh: 1020, cents: 31.98 }
    - { cents: 29.50 }
----

=== demand

A charge on your highest average power draw inside a window, priced per kilowatt per day and
billed against the single highest half hour in each reset period.

[source,yaml]
----
- type: demand
  from: "16:00"
  to: "21:00"
  days: ALL
  reset: MONTHLY
  centsPerKWPerDay: 20
----

[WARNING]
====
Demand tariffs are dominated by your worst half hour, not your average. Check the *heaviest day*
figure in the data-quality panel before assuming one suits you — a single unusual day can carry a
demand charge for a whole month.
====

=== controlledLoad

A separate, cheaper rate for energy on a controlled circuit — hot water, most often.

[source,yaml]
----
- type: controlledLoad
  cents: 12.10
  from: "23:00"   # optional: when the retailer energises the circuit
  to: "07:00"     # optional: both or neither
----

State both `from` and `to`, or neither. Neither means the circuit is energised all day, which is
how a plan that publishes no window behaves. A window may run past midnight.

Energy on the controlled circuit is read from a separate register in your interval file and is
never priced by the ordinary usage bands. Two rules follow, and both matter:

* A plan with *no* `controlledLoad` charge still charges for that energy, at its ordinary rate.
  A household with a controlled circuit still uses the energy, and leaving it unpriced would make
  every such plan look artificially cheap.
* Energy falling *outside* a stated window is likewise priced as ordinary consumption.

See xref:what-if.adoc#controlled-load[Hot water and the controlled circuit].

=== solarFeedIn

A credit per kilowatt hour exported. Contributes a negative amount to the bill.

[source,yaml]
----
- type: solarFeedIn
  cents: 3.3
----

Only meaningful if your data contains export readings, or you are running a solar what-if
scenario.

=== discount

Applied after every other charge.

[source,yaml]
----
- type: discount
  name: Pay on time
  basis: PERCENTAGE         # PERCENTAGE | FIXED
  scope: USAGE              # USAGE | SUPPLY | TOTAL
  value: 5                  # a percentage, or an amount in cents when basis is FIXED
  condition: pay every bill by its due date   # omit when the discount is unconditional
----

`scope` decides what the discount applies to. A discount advertised as "5% off" is almost always
`USAGE` only, not `TOTAL` — check the fine print, because the difference is the supply charge.

`condition` is free text rather than a flag because a retailer publishes a before- and an
after-discount column, and it is the after column that wins a comparison. Naming the condition
lets the comparison table and the plan detail page say what a total assumes, rather than only
that it assumes something. Where a plan carries a conditional discount, the comparison table
marks its total with an asterisk carrying the condition text, and the plan detail page shows the
condition in full. Omit `condition` and the discount is unconditional — no marker is shown.

== Rounding and precision

Every rate and quantity is held as an exact decimal, and rounding to cents happens once, at
display. Over 35,000 half-hourly multiplications, accumulating floating-point error would be a
real source of discrepancies against a printed bill.
